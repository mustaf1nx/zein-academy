# Безопасное обновление Zein Academy

Версия исходников: 1.1.0, 24.09.2026. Доступа к рабочему хостингу или базе при
подготовке архива не было. Все действия ниже выполняются владельцем сервера.

## 1. Сохраните рабочие данные и конфигурацию

Сделайте согласованную резервную копию базы средствами вашего хостинга/СУБД.
Для SQLite сначала остановите приложение и корректно сохраните базу вместе с
состоянием WAL, если он используется. Не копируйте открытую SQLite-базу произвольно.
Для PostgreSQL используйте штатный снимок/резервное копирование и проверьте его
восстановление в отдельную тестовую базу.

Сохраните текущую версию кода, `DATABASE_URL`, секрет JWT, настройки запуска и
приватные переменные окружения. Не помещайте резервную копию с данными учеников,
секреты или пароли в публичный Git-репозиторий.

**Не подменяйте production DATABASE_URL локальным значением из `.env.example`.**
Иначе приложение откроет новую пустую базу, что будет выглядеть как потеря учеников.
В комплекте исправлений намеренно нет рабочей базы и персональных записей учеников.

## 2. Сначала проверьте копию базы

Разверните эту версию отдельно, подключив восстановленную копию базы. Используйте
такую же СУБД и версию Python, как в рабочем окружении. Внесённые изменения
проверялись с SQLite на Python 3.13.5. PostgreSQL здесь не запускался; его SQL-путь
реализован, но должен пройти проверку на вашей тестовой копии.

`requirements.txt` обновлён до версий основных библиотек, использованных при
проверках. В нём больше нет Passlib/python-jose: пароли проверяются bcrypt,
JWT — PyJWT. Старые bcrypt-хеши не пересоздаются. Это изменение зависимостей,
поэтому не пропускайте установку и тест входа. Полная установка из PyPI в чистую
среду при подготовке архива не выполнялась. `psycopg2-binary` оставлен драйвером
PostgreSQL, его версия в исходном проекте не была закреплена.

Исходные файлы `runtime.txt`, `Procfile`, `railway.json` сохранены. В `runtime.txt`
указан Python 3.11.0, но этот конкретный runtime здесь не проверялся. Убедитесь,
какую версию фактически выбирает ваш хостинг, и выполните тесты в ней.

## 3. Подготовьте секреты и четыре аккаунта

`SECRET_KEY` обязан быть приватным и содержать не менее 32 байт UTF-8. Старое
встроенное значение отклоняется при запуске. Если существующий ключ надёжный,
оставьте его: это позволит сохранить совместимость подписей. Замена ключа
означает повторный вход сотрудников и перевыпуск подписанных ссылок.

Основной администратор `900101350123` остаётся администратором без обязательного
преподавательского раздела. Четырём дополнительным администраторам из исходного
кода добавляется `can_teach=true`:

| ИИН / логин из проекта | Исходное имя | Пароль при создании отсутствующего аккаунта |
|---|---|---|
| 555555555555 | Бекенов Берикбек | `ADMIN_TEACHER_1_PASSWORD` |
| 666666666666 | Айдынұлы Әкежан | `ADMIN_TEACHER_2_PASSWORD` |
| 777777777777 | Хайбуллин Минтимер | `ADMIN_TEACHER_3_PASSWORD` |
| 888888888888 | Админ | `ADMIN_TEACHER_4_PASSWORD` |

Для отсутствующего основного администратора используется `INITIAL_ADMIN_PASSWORD`.
Это существующие идентификаторы из исходников, а не проверка реальных ИИН или
подтверждение, что эти люди являются нужными четырьмя преподавателями.

Существующие имена, пароли и состояние активности не сбрасываются. Если аккаунт
был отключён, он не включается автоматически. Если вы хотите использовать других
четырёх сотрудников, задайте нужным администраторам `can_teach` через API управления
сотрудниками либо сначала измените согласованный список в `bootstrap.py` и миграции
до её первого выполнения. Не запускайте повторную миграцию вручную удалением её
маркера ради изменения списка пользователей.

При `SEED_ACCOUNTS=true` отсутствующие аккаунты создаются на старте. Приватные
пароли из переменных окружения должны занимать 8–72 байта UTF-8. При отсутствии
переменной генерируется случайный пароль, который сохраняется только в закрытый
файл `CREDENTIALS_DIR/initial_accounts_*.json` (по умолчанию `.secrets`).
Файл содержит секреты: перенесите их в менеджер паролей и удалите временный файл.
В Linux права файла 0600, папки 0700; в Windows отдельно проверьте ACL каталога.

На хостинге с временным файловым хранилищем заранее задайте начальные пароли через
приватные настройки платформы: сгенерированный файл может исчезнуть при redeploy.
Первичное создание выполняйте одним процессом. После успешного создания можно
поставить `SEED_ACCOUNTS=false` и убрать первоначальные пароли из окружения;
это не удалит созданные аккаунты. Изменение initial-переменной не сбрасывает пароль
существующего пользователя: для этого используется обычное изменение сотрудника.

## 4. Выполните обновление в окно обслуживания

Остановите все старые процессы приложения и фоновые обработчики, которые пишут
в эту базу. Старые и новые версии не должны одновременно сохранять посещаемость.
Обновите весь проект, а не только `index.html`.

```bash
python -m pip install -r requirements.txt
python migrations.py
```

Убедитесь, что миграция завершилась без ошибки. Она также вызывается при импорте
нового приложения, поэтому запуск сервера уже является операцией изменения схемы.
Миграция повторяемая: маркер `2026_09_lesson_snapshots_v1` предотвращает повторное
создание исторических отчётов. При ошибке выясните причину, а не удаляйте таблицы.

Затем запустите сервер обычной командой вашего хостинга. Для локальной проверки:

```bash
uvicorn main:app --host 127.0.0.1 --port 8080
```

Внешний порт, HTTPS и домен остаются настройками хостинга. `CORS_ORIGINS` обычно
пустой, поскольку страницы и API обслуживаются одним сервером. Для отдельного
frontend задавайте только конкретные доверенные origins. Часовой пояс:
`APP_TIMEZONE=Asia/Almaty`.

## 5. Сверьте старые уроки и зарплаты

Миграция не удаляет строки `attendance`, не меняет их исходный `recorded_by` и
сохраняет оценки, темы и домашние задания. Каждая прежняя пара «группа + дата»
получает одну историческую запись урока `slot_key=legacy`. Это не попытка угадать
несколько уроков одного дня по текущему расписанию.

Если в строках один сохранившийся автор, используется именно он, а не текущий
учитель группы. Отсутствующие/разные авторы, автор-администратор и дубли учеников
помечаются для ручной сверки. Если автор был перезаписан старой версией и это
никак не видно из сохранившихся строк, автоматически распознать ошибку невозможно.
Сверяйте с резервными копиями, журналом действий и подтверждёнными ведомостями.

Старая база не хранит историческую ставку. Для legacy-урока миграция фиксирует
ставку из профиля автора на момент обновления. **Это не гарантия ставки, которая
действовала в день старого урока.** Перед выплатой проверьте такие периоды.
Для новых уроков фиксируется ставка на момент первой сдачи отчёта.

Выполните только чтение на тестовой/рабочей базе для просмотра сомнительных записей:

```sql
SELECT id, group_id, date, teacher_id, teacher_name, lesson_rate,
       needs_review, provenance, review_note
FROM lesson_reports
WHERE needs_review = TRUE OR lesson_rate IS NULL
ORDER BY date, id;
```

Для проверки всех перенесённых ставок используйте фильтр
`WHERE provenance = 'legacy_recorded_by'`. Не снимайте `needs_review` массово без
проверки. Специальный интерфейс сверки старого авторства пока не реализован.
Итоговая зарплата при неоднозначных/неоценённых уроках обозначается как требующая
проверки вместо достоверной окончательной суммы.

## 6. Контроль после запуска

Проверьте вход старым паролем, меню одного из четырёх администраторов-преподавателей,
его назначенные группы, новый урок в 16:30 и дату начала месяца в отчётах. На
тестовых группах сдайте два разных предмета, смените преподавателя и убедитесь,
что прежние отчёты и суммы остаются у фактического автора. Проверьте разовую замену,
ошибку повторной отправки и наличие всех строк журнала после редактирования.

Сравните количество старых строк `attendance` до/после миграции. Сверьте несколько
известных зарплат вручную. После обновления клиентам следует перезагрузить страницу;
старый открытый интерфейс не должен продолжать работать с новым сервером.

Ссылки заморозки без подписи отключены намеренно. Сформируйте новые через карточку
ученика/приглашение: ссылка действует 30 дней и привязана к конкретному ученику.
Не публикуйте её: владелец ссылки получает разрешённые действия для этого ученика.

## 7. Откат

Храните согласованную пару «код до обновления + база до обновления». Не продолжайте
работу старого кода поверх базы, в которую новая версия уже записывала уроки: старый
алгоритм не понимает новую структуру и может нарушить историю. После новых записей
план отката нужно согласовать отдельно: восстановление старой резервной копии
потеряет изменения после момента копирования. Сначала сохраните текущее состояние
и определите, как перенести эти изменения, затем выполняйте подтверждённый откат.
